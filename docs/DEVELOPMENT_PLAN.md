## 二、最终产品定位

本项目最终定位为一个单租户、可部署的人工智能深度研究平台，而不是通用聊天机器人或通用智能体框架。

用户输入研究问题并可选上传文档，平台完成研究计划、网页检索、文档检索、证据分析、冲突核验和报告生成，同时展示引用来源、执行进度、模型调用、耗时、词元、失败与安全事件。

核心价值只保留三点：

1. 完成可追溯的深度研究闭环。
2. 展示多模型、RAG、安全和可观测性的工程实现。
3. 提供能够在面试中完整解释的前后端平台交付。

## 三、范围控制决策

### 3.1 主体功能是否继续扩展

主体功能不再横向增加新品类，但需要纵向补全当前已经承诺的能力。

后续开发重点不是增加更多 Agent、工具或模型厂商，而是让现有流程形成一个稳定、可测试、可展示的端到端产品。

### 3.2 必须完成的主体能力

- 单智能体深度研究流程：计划、收集、分析、验证、报告
- Qwen 与 DeepSeek 可选，支持聊天模型失败降级
- 聊天模型与 Embedding 模型独立配置
- 网页研究与用户文档 RAG
- FAISS 本地检索模式和 pgvector 平台检索模式
- 报告引用、来源片段和冲突证据说明
- 研究任务进度、取消、失败状态和执行轨迹
- 提示注入扫描、文件路径沙箱和密钥脱敏
- 研究任务历史、报告查看和 Markdown 下载
- 固定的小型离线评测集和可复现测试

### 3.3 明确不做

- 不做多智能体辩论、群体协作或自动角色生成
- 不做模型训练、微调、强化学习或自主进化
- 不继续增加新的模型厂商，界面只突出 Qwen 与 DeepSeek
- 不接入多个同类向量数据库，只保留 FAISS 与 pgvector
- 不做桌面控制、移动端控制或通用浏览器自动化
- 不提供任意 Python、Shell 或动态代码执行
- 不做企业级多租户、组织、复杂 RBAC、计费和订阅
- 不做多人实时协作、社交、推荐或插件市场
- 不做原生移动端、桌面客户端、语音和视频能力
- 不使用 Kubernetes，也不拆分为大量微服务
- 不建设大型评测平台，只维护能够覆盖核心风险的小型版本化评测集

## 四、目标技术架构

| 层级 | 技术 | 本项目职责 |
| --- | --- | --- |
| 前端 | Next.js、TypeScript、Tailwind CSS | 创建任务、上传文档、展示进度、报告、来源和历史 |
| API | FastAPI、Pydantic | 请求校验、任务接口、报告接口、SSE 进度推送 |
| 应用层 | ResearchService | 统一编排研究运行，不依赖命令行或网页框架 |
| 后台任务 | Celery、Redis | 执行长时间研究任务和保存临时进度 |
| 数据库 | PostgreSQL、SQLAlchemy、Alembic | 保存任务、报告、来源、轨迹和状态 |
| 向量检索 | FAISS、pgvector | FAISS 用于本地模式，pgvector 用于平台模式 |
| 文件存储 | 本地隔离工作区 | 首版使用本地存储并保留存储接口，不强制引入 MinIO |
| 模型 | Qwen、DeepSeek | Qwen 可同时用于聊天和 Embedding，DeepSeek 用于聊天 |
| 交付 | Docker Compose、GitHub Actions | 本地一键启动、检查和测试 |

平台首版是单租户个人部署，不实现完整注册登录系统。需要公开演示时，仅增加简单访问保护，不扩展为 SaaS 权限体系。

## 六、开发阶段

### P0：项目基线与范围收缩

状态：已完成

已完成项目裁剪、中文文档、模型路由、动态研究主题和基础离线测试。此阶段不再增加工作。

### P1：应用服务层

状态：进行中

目标：让命令行、测试和未来 FastAPI 通过同一个入口运行研究任务。

步骤：

- P1-1（已完成）：完善 `ResearchRequest`、`ResearchResult`、`ProgressEvent` 和状态枚举
- P1-M1（已完成）：清理全仓 Ruff 告警并建立可重复执行的规范检查基线
- P1-M2（当前维护步骤）：修复全仓类型契约问题并建立 mypy 检查基线
- P1-2：实现 `ResearchService`，统一初始化、执行、异常转换和资源释放
- P1-3：让现有命令行入口只负责解析参数并调用 `ResearchService`
- P1-4：移除研究主路径上的全局初始化和明显导入副作用
- P1-5：增加确定性离线端到端测试

验收标准：

- 命令行通过 `ResearchService` 完成一次离线研究任务
- 任务返回统一结果而不是只输出日志
- 进度事件可以被测试收集
- 失败、取消和超时具有明确状态
- 不调用真实 API 也能完成核心测试

### P2：研究闭环与安全加固

状态：未开始

目标：只完善现有深度研究主体，不增加新的业务方向。

步骤：

- P2-1：固化计划、收集、分析、验证、报告五阶段状态
- P2-2：统一来源、证据片段、内容哈希和引用模型
- P2-3：打通文档上传、解析、切分、FAISS 索引和检索
- P2-4：实现提示注入扫描、来源隔离和安全事件记录
- P2-5：实现重试、模型降级、取消和部分失败报告
- P2-6：建立小型版本化评测集

验收场景：

1. 仅使用网页来源生成带引用报告。
2. 使用本地文档 RAG 生成报告。
3. 主模型失败后降级到备用模型。
4. 恶意文档中的提示注入被识别并隔离。
5. 来源互相冲突时，报告明确展示分歧。

### P3：FastAPI 平台后端

状态：未开始

目标：将稳定的 `ResearchService` 暴露为平台 API。

首版接口边界：

- `POST /api/research-tasks`：创建研究任务
- `GET /api/research-tasks/{task_id}`：查询任务状态
- `GET /api/research-tasks/{task_id}/events`：通过 SSE 获取进度
- `POST /api/research-tasks/{task_id}/cancel`：取消任务
- `GET /api/research-tasks/{task_id}/report`：获取报告
- `POST /api/files`：上传研究文档

验收标准：OpenAPI 文档可用，接口模型完整，错误码统一，离线集成测试通过。

### P4：任务队列、持久化与平台 RAG

状态：未开始

目标：使研究任务能够脱离 API 进程执行并保存历史。

步骤：

- P4-1：使用 PostgreSQL 保存任务、报告、来源和事件
- P4-2：使用 SQLAlchemy 与 Alembic 管理模型和迁移
- P4-3：使用 Redis 与 Celery 执行后台任务
- P4-4：增加 pgvector 存储实现，同时保留 FAISS 本地实现
- P4-5：实现任务恢复、重复提交保护和过期文件清理

验收标准：API 重启后任务历史仍存在，Worker 可独立运行，同一文档不会重复索引。

### P5：Next.js 用户界面

状态：未开始

目标：完成一个面试时可以直接演示的研究平台。

页面范围：

- 新建研究：主题、模型、文档和研究设置
- 研究进度：阶段、日志、来源数量、取消按钮
- 研究报告：Markdown、引用、证据和下载
- 历史任务：状态、时间、模型和报告入口

明确不增加后台管理、复杂账号、计费和多人协作页面。

验收标准：用户不修改代码即可创建任务、观察进度并下载报告。

## 七、强制开发流程

### 7.1 每次修改前

1. 阅读本文档的“当前指针”和对应阶段。
2. 向用户明确报告当前阶段、当前完成度和下一步工作。
3. 检查 Git 工作区和上一步验收结果。
4. 确认本次改动只属于当前步骤，不顺带加入范围外能力。
5. 如果必须调整路线，先修改本文档的范围或决策，再修改代码。

### 7.2 每一步完成后

1. 运行与风险相匹配的测试、静态检查和安全检查。
2. 更新“当前指针”。
3. 更新“当前完成度”和对应阶段的状态。
4. 在“开发记录”中写明改动、验证结果和下一步。
5. 同步 README、技术需求或接口文档中受影响的内容。
6. 再提交并推送代码；默认测试通过后直接推送 `main`。

### 7.3 状态定义

- 未开始：没有代码或只有占位说明
- 进行中：已经实现一部分，但没有达到本阶段验收标准
- 已完成：代码、测试和文档均达到验收标准
- 阻塞：存在需要用户决定或外部条件才能继续的问题

## 九、面试解释口径

可以用下面这条主线解释整个项目：

> 这是一个单租户深度研究平台。用户提交研究主题和可选文档后，系统通过单智能体完成计划、检索、RAG、证据验证和带引用报告生成。项目支持 Qwen 与 DeepSeek 路由，使用 FastAPI 和后台任务执行长流程，使用 PostgreSQL 与 pgvector 保存任务和知识，Next.js 展示实时进度、证据和报告。为了控制范围，我没有扩展多智能体、训练、企业权限和复杂微服务，而是重点保证研究闭环、安全边界、可观测性和可复现测试。

面试中应重点解释：

- 为什么使用单智能体而不是多智能体
- 为什么聊天模型和 Embedding 模型需要解耦
- 为什么本地使用 FAISS、平台使用 pgvector
- 为什么研究任务需要后台队列和 SSE
- 如何处理提示注入、文件越权和密钥泄露
- 如何通过确定性模型和固定评测集保证可测试性
